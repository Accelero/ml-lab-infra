# Architecture

A single Hetzner VM running K3s, accessible exclusively through Tailscale. All services sit behind
the Tailscale operator's ingress proxies. No public ports are opened beyond UDP 41641 (Tailscale
peer communication).

```text
Your laptop (on Tailscale)
         │  Tailscale MagicDNS
         ▼
 ┌─────────────────────────────────────────────────┐
 │  hub-server (Hetzner CX33, Debian)              │
 │  K3s bound to tailscale0                        │
 │                                                 │
 │  [tailscale ns]                                 │
 │    tailscale-operator                           │
 │         │ IngressProxy: mlflow                  │
 │         │ IngressProxy: skypilot                │
 │         ▼                                       │
 │  [app ns]                                       │
 │    MLflow          SkyPilot API server          │
 │         │                   │                   │
 │         └─────────┬─────────┘                   │
 │                   ▼                             │
 │  [infra ns]                                     │
 │    CloudNativePG Postgres                       │
 │         │ WAL archive (continuous)              │
 └─────────┼───────────────────────────────────────┘
           │
           ├──► S3: backups bucket (WAL + base backups)
           │
           └──► S3: artifacts bucket (MLflow runs)

SkyPilot dispatches jobs to:
  RunPod GPU nodes ◄── ephemeral Tailscale auth key injected per job
       │
       └──► reaches MLflow and Postgres over Tailscale (not the public internet)
```

## Layers

The stack is built in four sequential layers. Each layer depends on the previous.

### Layer 1: Hub server (`infrastructure/hub_server.py`)

Creates the Hetzner VM and establishes its identity.

- **ED25519 SSH key pair**: generated by the Pulumi TLS provider, never written to disk. The public
  key is registered with Hetzner; the private key is used by subsequent layers to SSH into the
  server.
- **Tailscale auth key**: a non-reusable, ephemeral, preauthorized key tagged `tag:hub-server`.
  Expires after 1 hour. Injected into the cloud-init script.
- **Hetzner firewall**: opens UDP 41641 (Tailscale peer communication) inbound. All other inbound
  traffic is blocked at the network level. SSH over the public IP is not needed after Tailscale
  joins.
- **Hetzner server**: Debian 13, configured type and location (default: `cx33`, `fsn1`). The
  cloud-init script (`scripts/cloud-init.sh`) runs on first boot: waits for apt locks, creates a
  2 GB swap file, installs Tailscale, enables IP forwarding, and joins the tailnet.
- **TailscaleDeviceCleanup**: a custom resource that deregisters the hub-server from the tailnet on
  `pulumi down`.

### Layer 2: K3s cluster (`infrastructure/hub_cluster.py`)

Installs K3s over SSH, bound to the Tailscale interface.

- Resolves the K3s version: channel names like `stable` are resolved to a pinned release via the
  K3s update API.
- Installs K3s with `--flannel-iface=tailscale0` and `--node-ip=<tailscale-ip>`, so the apiserver
  and pod traffic use the Tailscale overlay, not the public NIC.
- Fetches the kubeconfig from the server and patches `127.0.0.1` to the server's Tailscale IP.
  The patched kubeconfig is used by the Pulumi Kubernetes provider and exported as a secret stack
  output.

### Layer 3: Tailscale ACL and OAuth (`infrastructure/tailscale.py`)

Configures the tailnet policy and creates OAuth clients for Kubernetes workloads.

- **Kubernetes operator OAuth client**: scopes `auth_keys` + `devices:core`, tagged
  `tag:k8s-operator`. Used by the Tailscale Kubernetes operator to create auth keys for ingress
  proxies.
- **SkyPilot OAuth client**: scope `auth_keys`, tagged `tag:skypilot-server`. Mounted into the
  SkyPilot pod as environment variables so the admin policy can create per-job auth keys.
- **ACL policy**: applied via the Tailscale provider. See the Networking section below.

### Layer 4: Applications (`infrastructure/apps.py`)

Deploys all Helm charts and Kubernetes manifests onto the cluster.

**Namespaces:**

| Namespace | Contents | Pod security |
| --- | --- | --- |
| `tailscale` | Tailscale operator | baseline |
| `infra` | CNPG operator, Postgres cluster | baseline/restricted |
| `app` | MLflow, SkyPilot API server | baseline/restricted |

**Helm releases (in order):**

1. **tailscale-operator**: creates `IngressProxy` resources for `mlflow` and `skypilot`.
   A `TailscaleDeviceCleanup` resource deregisters the operator itself on teardown.
2. **cloudnative-pg**: the CNPG operator in `cnpg-system`.
3. **PostgresCluster** (custom resource): creates the Postgres cluster with two databases
   (`mlflow_db`, `skypilot_db`). See the Backup and restore section.
4. **mlflow**: experiment tracking server. Uses Postgres as the tracking backend and S3 for
   artifact storage. Exposed via Tailscale ingress at `mlflow`.
5. **skypilot**: API server for job dispatch. Uses Postgres for job state. Mounts the admin policy
   configmap at `/sky-policies`. Exposed via Tailscale ingress at `skypilot`.

## Networking

### Tailscale ACL

The ACL policy enforces least-privilege between tagged devices:

| Source tag | Can reach |
| --- | --- |
| `tag:k8s-operator` | `tag:k8s` operator proxies, internet (HTTPS cert issuance) |
| `tag:k8s` | Other `tag:k8s` operator proxies |
| `tag:hub-server` | `tag:k8s`, `tag:k8s-operator` |
| `tag:skypilot-server` | `tag:hub-server`, `tag:k8s` |
| `tag:skypilot-node` | `tag:mlflow` and `tag:skypilot-api`, TCP 443 only |
| `autogroup:admin` | everything |
| `autogroup:member` | `tag:k8s` services only |

SkyPilot GPU nodes use `tag:skypilot-node`. MLflow and SkyPilot ingress proxies carry
`tag:mlflow` and `tag:skypilot-api`, respectively, alongside `tag:k8s`. The Kubernetes
operator owns both application tags. `tag:skypilot-server` identifies the OAuth client
that provisions workers; it is separate from the SkyPilot ingress tag.

Workers reach MLflow and the SkyPilot API over HTTPS. They upload artifacts directly
to the public S3 endpoint using internet egress and the supplied bucket credentials.
The worker grant does not allow direct access to Postgres, the hub, or other operator
proxies. The policy includes TCP and UDP tests that Tailscale validates when applied.
The operator depends on the ACL so the application tags exist before provisioning.

### Kubernetes network policies

Both `infra` and `app` namespaces have default-deny ingress policies. Egress is not
restricted. Explicit ingress allow rules are added on top:

- `app` namespace pods accept ingress only from the `tailscale` namespace (operator proxies).
- `infra/postgres` accepts ingress from `app` on port 5432 and from `cnpg-system` (the operator).

## Backup and restore

### Backup

Postgres data is continuously archived to S3 via barman (CloudNativePG's built-in archiver):

- **WAL archiving**: every completed WAL segment is uploaded to `s3://<bucket>/postgres/` as it is
  written. Compression: gzip.
- **Scheduled base backup**: daily at 03:00 UTC via a `ScheduledBackup` CR. Base backups land in
  `s3://<bucket>/postgres/base/`.
- **Initial base backup**: a new cluster without a completed base backup takes one immediately
  and verifies its WAL coverage before application deployment can proceed.
- **Retention**: controlled by `backup:retentionPolicy` (default `1w`). Barman enforces this after
  each base backup.

### Graceful teardown

The `PostgresCluster` custom resource (`resources/postgres_cluster.py`) blocks `pulumi down` until
data is safely archived:

1. Deletes the `ScheduledBackup` CR to prevent new backups from starting.
2. Waits for any in-flight backups to complete. An observed active backup failing aborts teardown.
3. Disables connections to the application databases and terminates their sessions.
4. Creates a unique restore point and switches WAL to close its segment.
5. Requires a completed base backup for the live PostgreSQL system and checks every required
   nonempty WAL object in S3 through the cutoff, including timeline ancestry and history files.
6. Saves the verified backup and cutoff in a ConfigMap, then deletes the `Cluster` CR.
7. Waits for all Postgres pods to terminate before returning and releasing dependent credentials
   and infrastructure.

Teardown never starts a new base backup. Its archive gate polls for up to ten minutes; missing
objects or any verification error abort teardown before cluster deletion. Backup and pod waits
also raise on timeout. Pod termination alone is not evidence of successful archival.

If the archive gate fails, the provider restores the previous database connection settings.
A retry after the Cluster has disappeared or started terminating requires the saved cutoff and
rechecks its S3 coverage. The checkpoint survives Cluster deletion and is cleared before a
subsequent startup accepts application writes.

The S3 check verifies completed backup metadata, base-data archive presence, and WAL object
coverage. It does not prove that their contents are readable or free of corruption. Periodic
restore tests remain necessary. Validation currently supports full Barman backups without
custom tablespaces and gzip or uncompressed WAL, matching this stack's configuration.

### Restore

On `pulumi up`, `PostgresCluster.create()` reads Barman metadata under
`s3://<bucket>/postgres/base/` using boto3. It requires `status=DONE`, consistent backup metadata,
and a nonempty base-data archive. If a completed backup exists, recovery uses its explicit ID:

- Points barman at the S3 backup source.
- Sets `cnpg.io/skipEmptyWalArchiveCheck: enabled` to avoid a false-positive check on the newly
  created cluster before it archives its first WAL.

If the archive is empty (first deploy), the cluster bootstraps via `initdb`, creating the two
databases and roles, and completes its initial base backup. An archive containing WAL or
incomplete backups without a completed base is rejected rather than overwritten by a new
cluster. An existing unready Cluster is waited on, never automatically deleted and recreated.
After recovery, the provider reopens the application databases disabled at the teardown cutoff.

## SkyPilot Tailscale injection

Every SkyPilot job automatically joins the tailnet. This is implemented via an admin policy
(`scripts/skypilot_policies.py`) that mutates the task at submission time.

### Admin policy chain

`SkyPilotAdminPolicy.validate_and_mutate` calls each sub-policy in `_policies` in order. The
current chain contains one policy: `_TailscalePolicy`.

`_TailscalePolicy.validate_and_mutate` does the following:

1. Reads `TAILSCALE_OAUTH_CLIENT_ID` and `TAILSCALE_OAUTH_CLIENT_SECRET` from the SkyPilot pod
   environment (populated from the `skypilot-tailscale-secret` Kubernetes secret).
2. Exchanges the credentials for a short-lived bearer token via the Tailscale OAuth endpoint.
3. Creates a one-time ephemeral preauthorized auth key for `tag:skypilot-node` (expires in 300
   seconds).
4. Injects `TAILSCALE_AUTH_KEY` into the task's environment variables.
5. Prepends `scripts/tailscale_setup.sh` to the task's setup script.

### Tailscale setup script

`scripts/tailscale_setup.sh` handles two runtime environments:

- **Systemd (cloud VM)**: tailscaled is already running via systemd after `tailscale install.sh`.
  The script brings up Tailscale with the injected auth key.
- **Non-systemd (Docker container)**: starts `tailscaled` in userspace networking mode
  (`--tun=userspace-networking`) with a SOCKS5 proxy on `localhost:1055`. Writes proxy settings to
  `/etc/profile.d/`, `/etc/environment`, and `/etc/bash.bashrc` so all subprocess invocations
  (pip, boto3, etc.) route through Tailscale.

To add a new sub-policy, subclass `sky.AdminPolicy`, implement `validate_and_mutate`, and append
the class to `SkyPilotAdminPolicy._policies` in `scripts/skypilot_policies.py`. Running
`pulumi up` applies the change.
